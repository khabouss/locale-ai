# Changelog

## 0.7.32

Found by running translated output through each platform's real toolchain — Android `aapt2`, a .NET 8 app with satellite assemblies, Flutter `gen-l10n` + `flutter test`, and Rails' `i18n` gem:

- **.NET/Python format items with a format spec lost their braces** ([khabouss/locale-ai#80](https://github.com/khabouss/locale-ai/issues/80)) — `{0:P0}` → `0:P0`, `{0:C2}` → `0:C2`, so `string.Format` printed them literally. `{index[,align]:format}` (and Python's `{price:.2f}`) is now a protected placeholder.
- **Currency amounts were changed by the model** ([khabouss/locale-ai#81](https://github.com/khabouss/locale-ai/issues/81)) — "Price €5" came back as "$5" (ar) and "5 yuan" (ru). A currency amount is now protected.
- **@handles were dropped or mangled** ([khabouss/locale-ai#82](https://github.com/khabouss/locale-ai/issues/82)) — "Contact us @support" lost the handle (fr) or turned it into debris. A standalone `@handle` (or Android `@string/name`) is now protected; e-mails, vue-i18n's `@:key` and `%@` are unaffected.
- **Android: a CDATA value was written back as plain markup** ([khabouss/locale-ai#83](https://github.com/khabouss/locale-ai/issues/83)) — aapt2 then stored a styled string, so `Html.fromHtml(getString(...))` lost its link in every translation. Written back as CDATA now, with Android's backslash escapes still applied inside it.
- **The tag-text fix lowercased German nouns** ([khabouss/locale-ai#84](https://github.com/khabouss/locale-ai/issues/84)) — "<a>begriffsbestimmungen</a>". German keeps the model's capital.
- **Nightly real-world suite** now also builds Android resources with `aapt2`, runs a .NET app with `.resx` satellite assemblies, and resolves Rails YAML with the `i18n` gem.
- **README**: per-language review notes from the real-project testing, and a "Reporting problems" section; **issue templates** for bug reports and bad translations.

A tool-written string that lost a protected term, or that a glossary entry now covers, is re-translated on a normal run; hand edits are never touched.

- **Nightly real-world regression suite** ([khabouss/locale-ai#77](https://github.com/khabouss/locale-ai/issues/77)) — `test/realworld.test.ts` checks real fr/es/de models against real tools (`msgfmt -c`, `xmllint`): placeholders inside tags, python-format `.po`, Angular XLIFF, second-run no-ops. Verified to fail on 0.7.29's code for each bug it guards against.

## 0.7.30

- **Regression in 0.7.29: the untranslated-tag pass corrupted placeholders, e-mails and URLs inside tags** ([khabouss/locale-ai#65](https://github.com/khabouss/locale-ai/issues/65)) — a tag text the model correctly kept unchanged, like `<em>%(title)s</em>` or `<a href="mailto:…">help@example.com</a>`, was taken for untranslated English and re-translated alone without placeholder masking: `%(titre)s`, `%(título)s`, `help@ejemplo.com`, `https://ejemplo.com/docs`. A renamed Python format key fails Django's `compilemessages` and raises `KeyError` at runtime. Only a tag text that's plain words is re-translated now; anything the masker protects is left alone (0/32 damaged strings across 8 placeholder styles and 4 languages, down from 7/32).
- **An escaped `%%` in a python-format/c-format `.po` message came back as a single `%`** ([khabouss/locale-ai#66](https://github.com/khabouss/locale-ai/issues/66)) — Django's `makemessages` writes "10%% off"; the translation's lone "%" reads as a broken format directive, so `msgfmt -c` and `compilemessages` rejected the whole catalog. `%%` is now protected like `%s`.
- **Angular XLIFF: the ICU copy inside `<x id="ICU" equiv-text="…"/>` was translated, corrupting the target and breaking `ng build`** ([khabouss/locale-ai#63](https://github.com/khabouss/locale-ai/issues/63)) — when a template mixes text with an ICU expression, Angular extracts the ICU as its own unit and leaves a placeholder in the sentence whose `equiv-text` attribute carries a copy of it. That copy made the whole sentence look like an ICU message, so its options were translated inside the XML tag: invalid XML in Arabic (and `ng build --localize` failing for every locale), the attribute leaking into the visible French text, digits of the `xid` changed in German. An ICU expression is now only detected outside tag markup, so the whole `<x …/>` stays one protected placeholder.

## 0.7.29

- **Text inside an inline tag was often left in English, and nothing reported it** ([khabouss/locale-ai#59](https://github.com/khabouss/locale-ai/issues/59)) — "Immer noch stecken? <strong>Chat with us</strong>", "Lisez notre <link>return policy</link>". A tag text the model copies over unchanged while translating the rest of the string is now translated on its own and put back inside its tag (in its source's case: "<link>politique de retour</link>"). A capitalized name ("<b>Trailhead</b>") is kept as it is; anything else still in English is reported as `untranslated-tag`.
- **next-intl's `<link>…</link>` (and any other void-element name used as a rich-text tag) was masked as a broken pair** — `link` is an HTML void element, so `<link>` was read as self-closing and `</link>` as a stray closer, which no model could follow; the string fell through to the last-resort strategy with its link text left in English. A void name that's closed in the same string is now an ordinary open/close pair.
- **`translate` didn't repair strings whose placeholders fail `check` unless `--overwrite`** ([khabouss/locale-ai#60](https://github.com/khabouss/locale-ai/issues/60)) — after upgrading, `check` reported the `{'@'}` literals and en→it dashes an older version broke, but `translate` said "0 strings translated" because the source hadn't changed, and `--overwrite` discards every hand edit. A string that's exactly what this tool last wrote (per the lock) but whose placeholders no longer match its source — including a lost dash — is now re-translated on a normal run. A hand-edited string is never touched, and a complex ICU message is left to its own structure check.

## 0.7.28

- **vue-i18n literal interpolation (`{'@'}`, `{'|'}`, `@:{'key'}`) was translated instead of protected** ([khabouss/locale-ai#55](https://github.com/khabouss/locale-ai/issues/55)) — the model rewrote it: `hello{'@'}harbor.cafe` came back as `hello.cafe.fr` (a different address) or `hello & quot؛ & quot؛ & quot؛ harbor.cafe`, and `@:{'brand'}` as `‘brand’`, while `check` passed. A `{'…'}` literal, the braced linked form `@:{'key'}`, and an e-mail address written with `{'@'}` (as one unit) are now masked like any other placeholder, so `check` also reports one that goes missing.
- **En/em dashes were lost or replaced with garbage by the en→it model** ([khabouss/locale-ai#56](https://github.com/khabouss/locale-ai/issues/56)) — `{open} – {close}` came back as `{open} [49] {close}` or `{open} € {close}`. `–` and `—` are now protected like `©`/`®`/`™`. `check` doesn't compare them, since a translator writing "de {open} à {close}" or a plain hyphen is legitimate.

## 0.7.27

- **Adding `locale-ai.config.json` after the first run silently dropped all change tracking** ([khabouss/locale-ai#53](https://github.com/khabouss/locale-ai/issues/53)) — the lock file lives next to the config file when there is one, otherwise in the locales folder, so adding a config (the README's own first step, for brand names) moved it to a new, empty lock. Existing translations then looked untracked: a source edit was never re-translated and `check` reported nothing stale. The old lock is now picked up, its file keys re-keyed relative to the new location, and moved next to the config on the next `translate`/`accept` (with a one-line notice); `check` reads it in place without writing anything.

## 0.7.26

- **Upgrading from 0.7.23 still lost change tracking for a flat dotted key, after one run with nothing to translate** ([khabouss/locale-ai#51](https://github.com/khabouss/locale-ai/issues/51)) — 0.7.25's fallback to the old, unescaped lock path (`"menu.save"`) only migrated the entry in the lock loaded at the start of a run, but the save step re-reads the lock from disk and prunes paths that no longer exist, so the old entry was deleted with nothing written under the new escaped path (`"menu\.save"`). A later source edit on that key was then silently ignored, and `check` reported it clean. Pruning now renames such a legacy entry onto its escaped path instead of deleting it (an entry already recorded under the escaped path wins per locale; an ambiguous legacy path is still pruned), so the migration sticks on any run, including a no-op one.

## 0.7.25

Four fixes for regressions that 0.7.24's own dotted-key-escaping and orphan-key-pruning fixes introduced, found by re-testing the published 0.7.24 against the round-8 fixtures plus new tests aimed at the changed code ([khabouss/locale-ai#49](https://github.com/khabouss/locale-ai/issues/49)):

- **`doNotTranslateKeys` no longer protected a flat key whose literal name contains a dot** — a top-level key named `"brand.name"` now produces the escaped path `brand\.name` (0.7.24's dotted-key fix), but `keyPathProtect` still compared it against the caller's unescaped `"brand.name"` and never matched, so a listed key got translated anyway. Both readings — the plain one (a nested `brand` → `name` pair, the common case) and the key escaped the same way a flat key of that name would be — are matched now.
- **Upgrading from 0.7.23 silently lost change tracking for a flat dotted key** — the old lock stored the unescaped path (`"menu.save"`); 0.7.24 looked up the new, escaped one (`"menu\.save"`) and found nothing, so the key looked never-tracked-but-already-translated (existing text, no staleness record), and a source edit on it was silently ignored from then on. `isSourceStale`/`isEdited` now fall back to the pre-0.7.24 unescaped path and migrate it onto the new key on the first hit.
- **A key pruned from a `.properties` target was written as `key=` (an empty value) instead of the line being removed** — worse than before 0.7.24's pruning existed at all: Java finds the key and uses that empty string rather than falling back to the English default. The line is now dropped when its key is absent from the built target altogether.
- **A key pruned from a YAML target was never actually removed** — the YAML writer edits the existing document in place and only ever sets or reorders paths the new data still has; nothing deleted a pair that fell out of it. `check` already reported these as orphans; `translate` now removes them too, without touching a merge-key pair itself.
- **README restructured as a landing page**: a quick start with a real before/after translation, a table of supported formats, a "Use in CI" GitHub Actions recipe, a flag table for `translate`, and one merged Languages section (quality tiers plus the benchmark table). The install warnings moved from the top into an "Installation notes" section.
- Per-format details moved from the README into [docs/formats.md](docs/formats.md), and the lock-file behavior into a new [docs/incremental.md](docs/incremental.md).
- Added format names (`gettext`, `xliff`, `xcstrings`, `android`, ...) to the npm `keywords`.

## 0.7.24

External review round 8, 14 confirmed bugs across every format, verified against real tools wherever possible (Ruby/Psych, `xmllint`, `msgfmt`/`ngettext`, the `@formatjs` ICU parser) rather than just this project's own simulators ([khabouss/locale-ai#44](https://github.com/khabouss/locale-ai/issues/44), [khabouss/locale-ai#46](https://github.com/khabouss/locale-ai/issues/46)):

- **YAML merge key (`<<: *defaults`) got moved to the end of its map, losing overrides under Ruby/Rails** — `reorderToMatch` sorts each map's pairs to match the translated data's own key order, but a merge key's contents were already flattened into its siblings by `toJS()`, so it wasn't one of those keys and sorted to the end instead. The `yaml` package (and PyYAML) give an explicit key priority over `<<` regardless of position, which is why this looked harmless — but Ruby's Psych (what Rails uses) applies `<<` where it textually appears, so a merge key moved after an overriding key silently discarded that override (verified against real Ruby, not just a simulator). `<<:` now stays exactly where it was in the source map (normally first).
- **XLIFF: escaped markup in the source (`&lt;b&gt;`) became a raw, unescaped tag on write, producing invalid XML** — `Use &lt;b&gt; tags…` was written as `Utilisez <b> balises…`, which `xmllint` rejects as a tag mismatch. The text is unescaped on read before translation, and on write `escapeXmlKeepTags` saw the literal `<b>` left behind and treated it as genuine markup to leave alone rather than text to re-escape. A new pattern recognizes the escaped-tag-text shape as its own opaque span, masked from the model and never unescaped/re-escaped.
- **Text inside an inline tag could come back emptied, silently dropping the link/bold text** — a `<a href="/terms">terms</a>`-shaped tag pair's content sometimes vanished entirely in the model's output (`<a href="/terms"></a>`). Detected and retried alone with the same literal-value mechanism `fixSingularGrammar` already uses, and reported if it still comes back empty. (A model translating some of the surrounding text but leaving a word inside the tag in English is a model-quality limit, not something a deterministic retry can reliably fix, and is left alone.)
- **A dotted JSON/YAML key collided with a nested one of the same path** (`"a.b"` alongside `"a": {"b": …}`) — both flatten to the same lock-file path string, so whichever was recorded last overwrote the other's entry, leaving it permanently "stale" and re-translated every run, and `check` always reported a false `placeholder-mismatch`/`stale` for one of them. A literal `.` (or `\`) within a key is now escaped before joining it onto a path.
- **`.po` Arabic plurals were written to the wrong `msgstr[]` slot** — Arabic's Plural-Forms formula puts the "zero" category at index 0 and "one" at index 1, but the write path assumed index 0 was always the singular ("one") slot. Confirmed with real `msgfmt`/`ngettext`: `ngettext(n=1)` returned the plural text and `n=0` the singular. The correct slot is now found by evaluating the target language's own Plural-Forms expression, not assumed.
- **Android `product`-qualified string variants collapsed into one, dropping the `product` attribute** — `<string name="title" product="tablet">` and `product="default">` are two distinct, device-specific resources, but keying by `name` alone collapsed them into whichever was read last, writing two identical `<string name="title">` elements (a duplicate-resource error under `aapt2`). Disambiguated only when a name actually repeats, so the common single-variant case is unaffected.
- **XLIFF 2.0 silently translated nothing** — the parser only recognizes 1.2's `<trans-unit>` shape, so a 2.0 file (`<unit><segment>`, `trgLang` instead of `target-language`) matched zero units: `translate` reported success with 0 strings translated and wrote an untouched copy. Rejected up front with a clear error instead.
- **Android's `formatted="false"` and `tools:ignore` attributes were dropped on every rewrite** — every `<string>`/`<string-array>`/`<plurals>` tag is rebuilt from scratch on write, with only `name`/`product`/`translatable` handled explicitly; `formatted="false"` (often required once a value mixes a bare `%s`/`%d` with other text, or `aapt2`'s format check fails) and `tools:ignore` (lint suppressions) are now captured and re-emitted verbatim.
- **The singular-grammar retry (wrong plural noun on a grammatically-singular string) only ever fired for i18next's `_one` suffix convention** — Android's `<plurals>` "one" item, gettext's own one-slot, and a nested Rails-style `{one, other}` YAML group are grammatically singular the same way and hit the same wrong-plural-noun bug, but were never recognized as such. Both the detection and the retry itself (previously hard-coded to `{{count}}` specifically) are now format-agnostic.
- **A target key whose source had been deleted or renamed lingered in the file forever, unreported** — only the lock file's record of it was ever pruned; the target file's own content, and `check`, never mentioned it. `check` now reports every such key as a new `orphan-key` issue (skipping a still-valid plural category), and `translate` now also removes one from the file itself, but only when the lock shows this tool wrote it for a source key that's since vanished — a key with no such history (added by hand, or by another tool) is left alone.
- **`.xcstrings` was reformatted on every single run, translated or not** — `JSON.stringify` writes `"key": value`; Xcode's own serializer writes `"key" : value` (a space before the colon too), so the whole file showed up in the diff every run purely from the spacing mismatch. Matched to Xcode's own spacing on write.
- **ARB's file-level `@@` metadata (`@@last_modified`, `@@x-generator`, ...) was dropped on write** — only `@@locale` was ever carried over (updated to the target tag); every other `@@`-prefixed key, not being locale-specific, is now copied over verbatim.
- **Flutter's default `lib/l10n` ARB folder wasn't auto-detected**, and the resulting error's hint could suggest the nonsensical `--from lib` — `lib` is Flutter's own source folder, not a locale directory, but its name happens to shape-match the hint's loose "looks like a locale" check, and a full recursive scan found the unrelated `lib/l10n/app_en.arb` several levels down. `lib/l10n` is now an auto-detected candidate, and the hint only looks directly inside a candidate directory rather than scanning recursively.
- **A UTF-16 (BOM) `.strings` target — Xcode's traditional default — was rewritten as plain UTF-8 on its very first run, even with nothing to translate** — the existing target was read with a plain UTF-8 decode instead of the same BOM-aware one every other read in this project already uses, so the comparison against the freshly serialized text never matched and the file was rewritten from scratch, losing its BOM. The target's encoding is now detected up front and matched on write.

## 0.7.23

Fixes two regressions from 0.7.22's curly-quote fix, caught by re-testing that release against real fr/de/it/es model runs and real `java.text.MessageFormat` via Docker ([khabouss/locale-ai#42](https://github.com/khabouss/locale-ai/issues/42)):

- **Possessives got a stray apostrophe** — the fix absorbed a curly quote on either side of a placeholder independently, so an unrelated trailing possessive (`{name}'s profile`) was swallowed into the same masked span as the placeholder. The exact text still restored verbatim, but the model could no longer see the `'s` as ordinary attachable text and lost the ability to restructure the sentence the way the target language needs (`Le profil {name}'s a été mis à jour.` instead of `Le profil de {name} a été mis à jour.`). A curly quote is now only absorbed when it forms a genuine matched pair of the same style directly wrapping the placeholder (`"{0}"` or `'{0}'`) — never a lone quote on just one side.
- **`check` failed correct translations** — because a matched curly-quote pair is now part of the placeholder's token text, a hand-edited translation using the target language's own quoting convention (German `„…“`, French `« … »`) or a rephrased possessive no longer counted as having the same placeholders as the source, so `check` reported `placeholder-mismatch` and exited 1 for valid translations. `check`'s placeholder comparison now ignores quote characters entirely when comparing source and target placeholder sets.

## 0.7.22

Fixes a third regression from 0.7.20, plus two related translation-safety gaps — one of them re-confirmed against real `java.text.MessageFormat`, not just a simulator — caught by re-testing 0.7.21 against real fr/de/it model runs ([khabouss/locale-ai#39](https://github.com/khabouss/locale-ai/issues/39), [khabouss/locale-ai#41](https://github.com/khabouss/locale-ai/issues/41)):

- **Editing an already-translated key to add `''{0}''` was never picked up by a rerun** — `readPropertiesDoc`'s write path looked up which argument indices used the quoted-value idiom in the *existing target file*, not the source, so an edit like `The name {0} is already taken.` → `The name ''{0}'' is already taken.` kept writing the old, substitution-suppressing `'{0}'` form no matter how many times `translate` ran afterward (the target line never had `''{0}''` of its own to find). This is the normal way the case comes up — a team that fixes a message in place already has translated files. The lookup now always comes from the source's own `quotedArgKeys`; only the unrelated `\uXXXX`-vs-raw-UTF-8 convention still follows the target.
- **A lone quoted brace (`'{'`) could be dropped or mangled by the translation model** — unlike `'{0}'`/`'{name}'`, whose content between the braces is already protected as a placeholder, a bare `'{'` had nothing recognizable for the masking pass to protect, so it reached the model as plain text (observed: a real en→fr hop dropped the brace and multiplied the quotes instead). It's now masked and restored verbatim like any other placeholder.
- **A curly quote (`"` `"` `'` `'`) directly touching a placeholder could garble the output in Italian and German** — `The file "{0}" was deleted.` came back as `Il file [55]{0} [56] è stato eliminato.`; the models handle the same quote characters fine elsewhere in a sentence, but garble this specific quote-against-brace boundary. Not `.properties`-specific — the same thing happened in JSON. `check` didn't catch it, since `{0}`/`{name}` was still technically present. A directly-touching curly quote is now masked together with the placeholder as one unit, so the model never sees the raw boundary.

**If you ran `translate` under 0.7.20**, any `''{0}''`-quoted message translated during that window was written as the wrong (substitution-suppressing) form, and neither `check`, a no-op rerun (the source hasn't changed), nor deleting the lock file will repair it — `translate` only re-translates when it detects something's changed. Delete the affected line(s) from the target file(s) (or the whole target file) and rerun `translate` to regenerate them correctly under this fix. The same applies to any message with a curly quote against a placeholder translated into Italian or German before this fix.

## 0.7.21

Fixes two more regressions from 0.7.20's elision fix, caught by re-testing that release against a real fr/de model run ([khabouss/locale-ai#37](https://github.com/khabouss/locale-ai/issues/37)):

- **`''{0}''` (MessageFormat's quoted-substituted-value idiom, common in Spring/Bean Validation messages) lost its value** — `unescapeProperties`'s `''`→`'` collapse on read turns `''{0}''` into the exact same text as `'{0}'` (the OTHER idiom, which suppresses substitution instead) before translation ever happens, so by write time there's no way to tell which one the source used from the text alone — 0.7.20's fix always guessed the suppressing one. Which argument indices used the doubled form is now captured straight from the raw source line, before that collapse, and carried alongside the key (the same way a `\uXXXX` convention already is) so write-time escaping doubles those quotes instead of protecting them, regardless of what the translated text looks like. Not strictly a new bug: 0.7.19 already broke this whenever the translation had no other apostrophe to coincidentally balance against (the German case); 0.7.20 broke it every time.
- **Quoting a lone brace (`'{'`) or a non-numeric braced name (`'{name}'`) got doubled, which then makes `MessageFormat` throw** — 0.7.20's literal-braces detection only recognized the `{N[,type]}`-shaped numbered-placeholder form. Broadened to any quote directly touching a brace — a balanced `{...}` run or a lone `{`/`}` — while still requiring direct touch, so the elision-regression fix from 0.7.20 stays intact.

## 0.7.20

Fixes a regression from 0.7.19's intentional-quoting fix, caught by re-testing that release against a real model run ([khabouss/locale-ai#35](https://github.com/khabouss/locale-ai/issues/35)):

- **Java `.properties`: two unrelated elisions in the same value were no longer escaped** — 0.7.19 judged a value's apostrophes "intentional `'{0}'`-style quoting" (and left them single) whenever they came out balanced overall — an even number of unpaired `'`s. But ordinary French/Italian text with two elisions, like `L'utilisateur n'a pas accès à {0}.`, pairs up by coincidence just as often as one genuine `'{0}'` idiom does; written with neither apostrophe doubled, `MessageFormat` reads the first `'` as opening a literal-quoted run that swallows "utilisateur n" from view. Apostrophes are now doubled individually, except for the exact two quotes directly wrapping a placeholder's braces (`'{0}'`, `'{0,number,integer}'`) — every other apostrophe is escaped regardless of how many others are in the string, including a lone one that merely sits next to an unrelated brace without a matching closing quote (elision right before a placeholder, as in `L'{0} n'existe pas`).

## 0.7.19

Another external review, 4 confirmed bugs, verified with fresh reproductions against the real source before fixing ([khabouss/locale-ai#33](https://github.com/khabouss/locale-ai/issues/33)):

- **A YAML anchor or alias crashed the whole file, writing nothing** — a plain alias used as a pair's value (`profile: *common`) threw `Error: Expected YAML collection at profile`, because `Document#setIn`/`getIn` only walk through real Map/Seq nodes and the node actually stored there is an `Alias`. Not a regression — 0.7.13 and 0.7.17 crash the same way. Every alias that stands in place of a collection is now replaced with an independent, anchor-stripped clone of what it points to before anything is written. A Rails-style merge key (`<<: *defaults`) didn't crash, but its `<<` subtree was read as an ordinary key holding its own nested copy of the merged-in strings, double-counting them alongside the anchor's own copy; parsing with the `yaml` package's `merge: true` option now flattens it straight into the map instead, and it's left untouched on write (a merge key already round-trips fine as-is).
- **The apostrophe fix (0.7.18) missed typed MessageFormat arguments** — the placeholder check only matched a bare `{0}`, not `{0,number,integer}` or `{0,date}`, so an apostrophe next to one of those stayed single and `MessageFormat` would still eat the placeholder. The check now matches the full `{N[,FormatType[,FormatStyle]]}` shape.
- **Intentional `'{0}'`-literal quoting was broken by the same apostrophe fix** — `Type '{0}' literally` (MessageFormat's own documented way to show a placeholder's braces literally, no substitution) was written as `Type ''{0}'' literally`, which un-protects the placeholder instead of keeping it literal — backwards from the intent. Apostrophes are now only doubled when they're *unbalanced* (an odd one out, like "don't"); a value whose quotes are already balanced is left exactly as written.
- **Android never escaped a literal backslash on write** — `Saved to C:\Temp` round-tripped unchanged, and Android's own unescaping then drops the backslash (its "unknown escape" rule), displaying `C:Temp`. Not a regression. New in 0.7.18: the `\uXXXX` decode on read ran as its own pass before the generic backslash fallback, so it couldn't tell a real `\uXXXX` escape from an escaped backslash immediately followed by the literal text `uXXXX` (`\\u0041`, meaning one backslash then "u0041") — it matched starting at the second backslash, decoded that as `U+0041` ("A"), and left the first backslash to be eaten by the next pass. Both escapes are now handled in one combined pass.

## 0.7.18

Another external review, 7 confirmed bugs plus one likely one, verified with fresh reproductions against the real source (not the reviewer's own scripts/clone) before fixing ([khabouss/locale-ai#31](https://github.com/khabouss/locale-ai/issues/31)):

- **A full disk during a model download made the CLI exit silently with code 0** — the write-stream's `'error'` listener (added in 0.7.14) caught `ENOSPC`, but the download loop was still only waiting on `'drain'`, which a stream that has already errored never emits again. With nothing else keeping Node's event loop alive, the whole process just exited on its own once the loop emptied — no thrown error, no log, exit code 0 (a CI run would read this as a pass). The wait now resolves on `'error'` too, so the `streamErr` check right after it actually runs.
- **YAML files with a bare numeric key got a duplicated, untranslated entry** — `errors: {404: Not found}` came out with BOTH a new `"404": <translated>` pair AND the original, untouched `404: Not found` left in place. YAML parses a bare `404:` as the JS *number* 404, while every key this tool's pipeline passes back in is always a JS *string* ("404", from `Object.entries()`); `Document#setIn` matches an existing pair by strict key identity, so the string lookup never recognized the number-keyed pair as the same key. Existing pairs are now matched and updated by their string form first, so only a genuinely new key still falls through to `setIn`.
- **Android `\uXXXX` escapes were corrupted on read** — `Loading…` was read as the literal text `Loadingu2026` (backslash dropped, `u2026` kept as-is) rather than decoded to "Loading…", since the unescape pass only recognized `\n`/`\t` before falling back to a generic "drop the backslash" rule for everything else. `\uXXXX` is now decoded to the real character first.
- **Android values starting with a literal `\@`/`\?` lost their escape on write, breaking the build** — `\@mention a teammate` round-tripped as plain `@mention a teammate…`, which Android's `aapt2` build tool then parses as a resource/style reference and fails on. A value whose first character is a literal `@`/`?` is now re-escaped on write (true `@string/`-style references were already, and remain, untouched by this — they take a separate raw-passthrough path).
- **`doNotTranslate` was ignored by the singular-grammar retry** — both the i18next `_one` retry (`fixSingularGrammar`) and the ICU `plural` "one" retry (`fixIcuOneUnits`, added in 0.7.14) built their literal-"1" retranslation input straight from the source string, bypassing the `doNotTranslate` mask the main pass already applied. A fake-model test showed the main pass correctly masking a protected term and the retry then sending it to the model raw; in a real run this also produced a stray capital letter. Both retries' eligibility check is now `doNotTranslate`-aware too, so a string containing both the count placeholder/hash and a protected term is disqualified from this narrow retry rather than leaking it unmasked.
- **`HF_TOKEN` could still be sent to a third party** — the 0.7.14 fix checked `HF_ENDPOINT.includes("huggingface.co")`, which a hostile endpoint can pass while still receiving the token, e.g. `https://huggingface.co.attacker.example` (a subdomain of attacker.example) or `https://attacker.example/huggingface.co` (the text appears only in the path). The check now compares the endpoint's parsed hostname exactly.
- **Java `.properties` values with a `{0}`-style placeholder could corrupt or lose a literal apostrophe when read by `java.text.MessageFormat`** — `Cannot open {0}` translated to `Impossible d'ouvrir {0}`, but `MessageFormat` (what typically interpolates a `{N}`-placeholder resource string) treats a bare `'` as the start of a literal-quoted run wherever `{N}` syntax appears, so the apostrophe would eat the placeholder or corrupt the text depending on where the next `'` falls. `''` is `MessageFormat`'s own documented escape for one literal apostrophe; values containing a `{N}`-shaped placeholder now get their apostrophes doubled on write and un-doubled on read. Values with no placeholder are left untouched, since plain `ResourceBundle.getString()` does no substitution and doubling there would just be visible noise.

Also investigated, and deliberately **not** fixed this round: **JSON (and residually, YAML) keys that look like array indices get silently reordered** — `{"title", "404", "500"}` comes out as `{"404", "500", "title"}`, because a plain JS object's own integer-like-shaped string keys are always enumerated in ascending numeric order before any other string key, per the ECMAScript spec, regardless of insertion order; this happens the moment the key is assigned on the object, not as a `JSON.parse`/`JSON.stringify` post-processing step, so there's no way to recover true source-text order once the data is held in a plain object. A safe fix needs either a from-scratch order-preserving JSON parser, or migrating JSON's read/write path onto the `yaml` package's own Pair-based `Document` model the way YAML already is — but prototyping that showed `Document#toString()` renders a JSON-sourced nested object/array in YAML's flow style (`{ "a": 1, "b": [ 1, 2, 3 ] }`) rather than `JSON.stringify`'s fully-expanded block style, a real formatting-regression risk for every existing JSON locale file with nested structure, not just ones with numeric keys. Deferred rather than risked under this round's scope; the numeric-key fix above still removes the duplication, the worse of the two symptoms.

## 0.7.17

- **Two concurrent `translate` processes for different locales could race on `locale-ai.lock.json`, silently losing one locale's history** — each process loaded the lock once at startup and wrote back that whole in-memory snapshot at the end, so whichever finished last overwrote the other's entries entirely (translated files on disk were unaffected; only the lock's staleness/edit-detection history for the "losing" locale was lost). The lock's save path now re-reads the file fresh from disk and merges in only the current run's own delta, under a cross-process file lock, so two runs' saves can no longer clobber each other ([khabouss/locale-ai#29](https://github.com/khabouss/locale-ai/issues/29)).

## 0.7.16

- **A legitimately empty source string (`""`) was re-"translated" on every run, forever** — `needsTranslation` treated any empty-string target as unfinished without checking whether the source is also empty, in which case an empty target is already the correct, final translation. - **The ICU `one` branch kept the plural noun** (fr: `one {# fichiers}` instead of `# fichier`) — the existing literal-"1" fix for i18next `_one` keys wasn't applied to ICU plurals. Extended to cover ICU `plural` "one" branches too.
- README's demo output still showed `locale-ai 0.7.11`; updated to this version.

Also investigated, and deliberately **not** shipped this round (see the issue for why): a "near-identical" brand-name warning (false-positive rate too high — it can't tell a botched respelling from a correct short cognate translation), a plural-form lexical mismatch between grammatical categories translated without shared context, and sentence-splitting losing cross-sentence grammatical context (needs a real interface change, not a local fix). tu/vous mixing, also flagged by the same review, turned out to be an artifact of the `<unk>` bug above and no longer reproduces.

## 0.7.12

Five more confirmed bugs, plus three doc/config hygiene items, from the same external review ([khabouss/locale-ai#18](https://github.com/khabouss/locale-ai/issues/18)):

- **The onnxruntime-node trimmer's "other consumer" check missed a symlinked sibling** — `Dirent.isDirectory()` reports `false` for a symlink, which is exactly how npm/yarn workspaces and `npm link` represent a linked package. A real consumer linked that way was invisible to the check, risking its binaries being deleted. It now follows symlinks (one level, and one level deeper for a scoped `@scope/pkg`) before deciding.

Removed in favor of setting `ONNXRUNTIME_NODE_INSTALL=skip` directly — the mechanism the README already recommends for an end-user install — in CI and in CONTRIBUTING's own setup instructions.

Changed to a name-only key, trusting any version of the package the way the dependency range already does.
- **README/CONTRIBUTING had three stale figures**: a demo output showing `locale-ai 0.6.3`, a post-trim install size given as both "~51 MB" and "~45 MB" (the real, measured number — confirmed again now — is ~45 MB), and an e2e-download-size comment/doc still saying "~115 MB" from before `tc-big` became the default `en-fr` model (it's ~345 MB now). `SECURITY.md` also now notes the two cases its "pinned and verified" guarantee doesn't cover: a project's own custom (unpinned) model config, and a custom `HF_ENDPOINT` serving both the file and the checksum that verifies it.

## 0.7.11

Five more confirmed bugs from the same external review, verified with reproductions before fixing ([khabouss/locale-ai#16](https://github.com/khabouss/locale-ai/issues/16)):

- **French punctuation used a plain, breakable space, not a non-breaking one** — before `! ? ; :`, both in the engine's own post-processing and the built-in glossary's "forgot password?"/"Password:" entries, so the punctuation could wrap onto its own line, orphaned at the start of the next one. All three sites (plus a third, previously-unreported one — the glossary's own French ":"-spacing rule) now insert `U+00A0` instead, and the engine's regex now replaces an existing plain space too, not just fills in a missing one — the model itself often adds the plain space.
- **Translating to `pt-BR` got the same Plural-Forms formula as `pt`** (European Portuguese, `n != 1`) instead of the gettext-conventional `n > 1` for Brazilian Portuguese, since the lookup had no distinct `pt-BR` entry and silently fell through to a generic fallback that happened to produce the same (wrong) formula. `pt-BR` now resolves correctly, ahead of the bare `pt` entry.
- **The generic Plural-Forms fallback was structurally wrong for untabulated Slavic/Baltic languages** (Croatian, Serbian, Bosnian, Lithuanian, Slovenian) — it only matched literal `n==1`, `n==2`, etc., so a number like 21 (which should be singular) fell into the wrong, catch-all category. These five languages now have their own correct, well-established gettext formulas instead of relying on the generic fallback.
- **`check` couldn't see inside a nested ICU plural/select** (`{count, plural, one {...} other {...}}`) at all — a dropped mandatory `other` category or unbalanced braces in a hand-edited translation passed every check silently, since the placeholder-comparison regex can't match across the inner `{...}` boundaries. `check` now parses the target's ICU structure directly and reports a new `icu-structure` issue when it doesn't parse.
- **The lock file and target locale files were written with a single, non-atomic `fs.writeFileSync`** — a process killed mid-write could leave a truncated file, which the lock loader (since 0.7.7) then hard-fails on. Both now write to a temp file in the same directory and rename it into place, so a reader (or a re-run after being killed) never sees a partial write.

## 0.7.8

Five more parsing/engine bugs from the same external review, verified with reproductions before fixing ([khabouss/locale-ai#10](https://github.com/khabouss/locale-ai/issues/10)):

- **Android `strings.xml`: `translatable='false'` (single quotes) wasn't recognized**, so a string marked that way was translated anyway. Both quote styles are now accepted.
- **Android `strings.xml`: a commented-out `<string>` not immediately followed by a real element was read as live content** — the parser only recognized a `<!-- ... -->` block as a comment when it directly preceded another tag; a standalone one (at the end of the file, or followed by another comment) was scanned straight through, and tag-shaped text inside it got picked up as a real entry. Every comment not immediately attached to a following element is now excluded from matching entirely.

- **XLIFF: a self-closing `<target/>` produced a duplicate `<target>` on write** — the parser didn't recognize it as an existing target to replace, so serialize inserted a brand-new one right after `</source>` while leaving the original self-closing tag in place too. It's now replaced in place like any other `<target>`.
- **The `_one` plural-grammar fix (retranslating with a literal "1" to get the right singular noun form) could restore the wrong "1".** If the source string already had its own unrelated literal "1" and translation reordered the two, the fix could silently freeze the actual count as a literal "1" while corrupting the unrelated one into `{{count}}`. It's now only applied when exactly one standalone "1" survives in the output — ambiguous results are left alone, keeping the normal (unfixed but uncorrupted) translation instead.

## 0.7.7

Six correctness gaps in the incremental lock/rebuild pipeline, from an external code review verified against the source before fixing ([khabouss/locale-ai#8](https://github.com/khabouss/locale-ai/issues/8)):

- **`_few`/`_many` plural forms, derived once from `_other`, were never resynced.** When `_other`'s source text changed and got re-translated, its already-derived `_few`/`_many`/etc. stayed frozen with the original wording forever, with no warning from `check`. They now resync whenever `_other` is re-translated — unless a translator hand-edited that specific derived form, in which case it's left alone and flagged as a conflict (same "never silently overwrite an edit" rule as every other key) instead of being resynced or re-flagged twice.
- **`locale-ai accept` with no keys given accepted every key, not just hand-edited ones** — silently marking a genuinely outdated (source-changed-since-translated) entry as reviewed too, so `check` stopped catching it. It now only auto-accepts entries actually flagged as edited; an explicit `accept <key>` still accepts that exact key unconditionally, and can now also clear a conflict on a plural-derived key (previously impossible, since derived keys have no source counterpart for `accept` to match against).
- **A lockfile that failed to parse was treated identically to a missing one** — silently discarded, then overwritten by the next save. Since the README tells teams to commit the lockfile, an unresolved merge conflict (stray `<<<<<<<` markers) destroyed all edit/staleness history with no warning. It now throws instead of guessing.
- **The project config was only looked up in the exact working directory.** Running from a subdirectory (or with `--input ../locales`) silently missed a `locale-ai.config.json` at the project root. It now walks up parent directories like eslint/prettier, stopping at the first `.git` it finds.
- **A translation that fell back to the untranslated source text was recorded as done**, and never retried on a later run. Such entries are now excluded from the lock, so the next run retries them.
- **The lock file was saved once, after every locale in a run finished**, so interrupting the process after locale 1 of 3 lost locale 1's lock updates too, even though its target file was already written. It's now saved after each locale finishes.

## 0.7.5

A follow-up round from the same external review:

- **There was no way to approve a hand edit.** Once the lock flagged a target string as "edited", it stayed flagged forever — the only way out was `--overwrite`, which re-translates everything and wipes every *other* hand edit too. `locale-ai accept [--to <locales>] [key...]` now records the current on-disk text as approved (for one key, several, or every key with none given) without touching the file or retranslating anything.

- **XLIFF dropped a translator's `state="final"`/`state="needs-review"` attribute** even on a run that retranslated nothing — any `<target>` got replaced with a fresh, attribute-less one regardless. An unchanged `<target>` is now left completely untouched.
- **A JS/TS locale module's same-line trailing comment (`home: 'Home', // note`) moved onto the next key** on a rewrite, so it looked like it described the wrong entry. It now stays attached to the key it was actually commenting on.
- A small changelog correction: the 0.7.0 entry below previously said that review "ran the CLI end-to-end against real cached models" — it actually used a stub translator, since the reviewer's sandbox couldn't reach Hugging Face. Speed/quality benchmarks and the quantization-batching tradeoff the same review asked about were already measured and documented (see the README's "Speed" and "Known limitations" sections); re-verified against real cached models as part of this round, numbers unchanged. ja/ko are likewise already a documented gap (no usable OPUS-MT model), not a new one.

## 0.7.2

Three Android `strings.xml` bugs found by the same external review, all from its regex-based parsing not accounting for Android-specific value conventions:

- **Inline markup (`<xliff:g id="...">...</xliff:g>`, Android's own placeholder-wrapper tag) came out HTML-escaped** — visible as literal `&lt;xliff:g...&gt;` text on screen instead of real XML. It's now written the same tag-protected way XLIFF's own inline `<x>`/`<g>` markup already was.
- **A value that's purely a reference to another resource (`@string/app_name`) was sent to the translation model.** It's now left alone and reproduced byte-for-byte, regardless of its own `translatable` attribute.
- **A value wrapped in a literal `"..."` pair — Android's convention for preserving leading/trailing whitespace — lost its quotes and that whitespace.** Both are now kept on write.

## 0.7.1

- **`npm install` could fail entirely on a network that can't reach `api.nuget.org`** — `onnxruntime-node`'s own postinstall tries to download a ~260 MB CUDA provider locale-ai never uses (CPU only), and that download failing took the whole install down with it, which is common behind corporate proxies and in locked-down CI. The README now documents `ONNXRUNTIME_NODE_INSTALL=skip npm install locale-ai` to skip it up front (also a faster install either way: ~51 MB / ~3s). As defense in depth, locale-ai now also re-runs its own CUDA-provider cleanup on every CLI invocation, not just at install time, since npm doesn't guarantee the postinstall that's meant to remove it runs after onnxruntime-node's own download finishes.

## 0.7.0

Fixes to `locale-ai.lock.json`, the incremental-translation lock file, found by an external review that ran the CLI end-to-end against a stub translator (not real models — the reviewer's sandbox couldn't reach Hugging Face):

- **Per-locale source tracking.** The lock used to store one source-string hash shared by every target locale. Translating `--to es` after editing a source string would mark that string "up to date" for `es` *and* for a `--to fr` run that hadn't happened yet — so `fr` silently kept the outdated translation. The hash is now tracked per locale.
- **Hand edits are never silently adopted.** A translator's edit to a target file is detected and reported for review, same as before — but it used to be recorded as if the tool itself had written it, so a later run would stop reporting it, and a subsequent source change would overwrite the edit with no warning at all. The lock no longer updates its "last written" record for a path unless this run actually (re)translated it, so an unresolved edit keeps being reported every run. If the source changes *while* an edit is still pending, that's now reported as a **conflict** instead of either side winning silently. `--overwrite` still forces past all of this when that's what you want.
- **The lock lives next to your config file (or the locale files) now, not wherever you happened to run the command from.** Running from a subdirectory with a relative `--input` used to create a second, empty lock there; the key paths inside it are now relative to the lock's own location too, so the same project always resolves to the same lock regardless of invocation directory.
- **`locale-ai check` now reads the lock.** A translation that's gone stale (source changed, target never re-run) is now a check failure, which was the main point of having a lock file for CI in the first place.
- **Deleted keys are pruned from the lock** instead of lingering forever.
- **First-run notice.** Creating the lock file for the first time now prints a line telling you to commit it.
- A pre-0.7.0 lock file is read and migrated automatically; nothing needs to be deleted or regenerated by hand.
